# FR-12: Dead-Reckoning Sensor Fusion And Drift Correction

## Requirement
> The system shall fuse dead reckoning estimates with periodic visual fixes to
> reset accumulated drift errors.

## Rationale
When GNSS is degraded, denied, or unavailable, the navigation stack still
needs a continuous position estimate between visual localizations. FR-10
introduced a standalone IMU-based dead-reckoning source, and FR-11 provides
periodic absolute visual pose fixes. This requirement connects the two: dead
reckoning acts as the continuous slave estimate, while each trusted visual fix
acts as the master correction that re-anchors the DR state and clears
accumulated drift.

## Acceptance Criteria
1. **[Met]** Dead reckoning is used as the continuous estimate when GNSS is
   degraded, denied, or unavailable.
2. **[Met]** Each valid high-confidence visual fix resets accumulated
   dead-reckoning drift by resetting the DR state to the visual pose.
3. **[Met]** From the point of view of current `PositionBlender` consumers, the
   output format remains unchanged: a geodetic `(lat, lon, alt)` tuple plus a
   navigation-mode string.
4. **[Met]** The GNSS-healthy fast path remains preserved and uses GPS directly
   as the trusted source.
5. **[Met]** When no valid visual fix is available, the system continues in
   DR-only mode rather than falling back to GPS/vision weighted averaging.
6. **[Met]** Unit and integration tests validate visual drift reset, output
   compatibility, DR-only behavior, and the preserved GPS-healthy path.

## Test Plan

### Unit Tests
- Verify a high-confidence visual fix snaps the fused pose to the visual
  correction and resets the dead-reckoning state.
- Verify subsequent DR propagation continues from the corrected pose instead of
  the pre-reset drifted pose.
- Verify DR-only operation continues without visual fixes and without resetting
  accumulated drift.
- Verify the GPS-healthy path preserves the existing output contract and does
  not allow DR/vision corrections to override healthy GPS output.

### Integration Tests
- Verify `VnsRuntime` supplies IMU-driven dead-reckoning estimates to the
  blender when localization fails under GNSS denial.
- Verify `VnsRuntime` passes successful visual fixes through the blender and
  resets the underlying dead-reckoning state.
- Re-run the core/runtime/interface regression surface to confirm logger,
  MAVLink-facing, GNSS-monitor, and legacy blender behavior remain compatible.

### Simulation Tests
- Future follow-up: validate live PX4 SITL / Gazebo behavior with actual IMU,
  GNSS denial, and periodic visual fixes in-flight. This repository change does
  not include a full SITL run.
