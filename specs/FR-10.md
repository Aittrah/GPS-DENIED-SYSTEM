# FR-10: Dead Reckoning Navigation

## Requirement
> The system shall estimate the UAV's position and orientation using dead
> reckoning based on calibrated inertial sensor data.

## Rationale
When GNSS and visual localization are degraded or unavailable, the navigation
stack still needs a continuous local motion estimate derived from IMU data.
This requirement introduces a standalone dead-reckoning source that propagates
pose, velocity, and attitude from calibrated inertial samples while allowing
conservative gyro / accelerometer bias compensation inside the propagator
itself. Keeping FR-10 standalone preserves a clean handoff to FR-12, where
GPS/vision correction policy and bridge limits are enforced separately.

## Acceptance Criteria
1. **[Met]** Dead reckoning produces continuous position, velocity, and
   orientation estimates from calibrated IMU data in the project's existing
   local navigation convention.
2. **[Met]** Configurable gyro and accelerometer bias vectors are subtracted
   before quaternion and translational propagation.
3. **[Met]** The update method supports at least a 100 Hz sample cadence.
4. **[Met]** Output uses the existing core coordinate convention and units:
   local NED metres for position/velocity and radians for roll/pitch/yaw.
5. **[Met]** The module exposes bridge-age / confidence decay state for
   trusted corrections without directly fusing GPS or visual measurements.
6. **[Met]** The module remains importable without ROS2 installed.
7. **[Met]** Unit tests validate zero-bias regression, bias compensation,
   drift behavior, confidence aging, bridge expiry, 100 Hz cadence, and
   ROS2-free import/use.
8. **[Met]** Non-strictly-increasing IMU sample timestamps (duplicates,
   out-of-order/stale samples, and large backward clock jumps) do not raise
   exceptions; they are handled per a defined policy — duplicates and small
   backward steps are skipped and counted, large backward jumps re-anchor
   timing safely without resetting position/velocity/orientation, and
   excessively large forward gaps are clamped to a configurable maximum
   integration step — and the module exposes read-only counters
   (`duplicate_sample_count`, `stale_sample_count`, `timestamp_reset_count`,
   `clamped_dt_count`) plus a `last_update_outcome` for each outcome.

## Linked Source Files
- `src/vns/core/dead_reckoning.py` - standalone strapdown-style dead-reckoning implementation, including the non-monotonic IMU timestamp classification policy (duplicate/stale/reset/clamp) in `_resolve_dt`.
- `src/vns/core/models.py` - shared `IMUSample` input carrier and `UAVState` estimate type.

- `tests/unit/test_dead_reckoning.py` - synthetic integration, drift, cadence, importability, and duplicate/stale/reset/clamp timestamp-robustness coverage.

## Test Plan

### Unit Tests
- Verify deterministic integration for constant acceleration and constant yaw rate.
- Verify configured gyro and accelerometer bias vectors are removed before propagation.
- Verify stationary or near-stationary calibrated IMU input does not accumulate large numerical drift over a fixed interval.
- Verify trusted corrections reset bridge age/confidence and the next timestamped IMU sample integrates immediately.
- Verify confidence decays over time and reaches zero once the configured bridge duration expires.
- Verify explicit `dt` updates and timestamp-derived updates behave consistently at 100 Hz.
- Verify importing and using `DeadReckoning` does not require ROS2.
- Verify duplicate, out-of-order/stale, large-backward-jump, and excessive-forward-gap IMU timestamps are handled without raising, per a defined classification policy, and are exposed via read-only counters.

### Integration Tests
- Re-run the existing core/runtime/interface regression surface to confirm dead reckoning remains standalone and does not break GNSS, blending, or MAVLink behavior.

### Simulation Tests
- Future follow-up: connect the standalone class to live IMU topic handling and validate behavior against Gazebo trajectories without fusing into GPS/vision.
